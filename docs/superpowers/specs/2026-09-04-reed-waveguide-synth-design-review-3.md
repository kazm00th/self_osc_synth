### R48. γ 定数の順序不変条件が未記述 — 測定値次第で `γ_base` の範囲が反転・消滅する（§5 :374-378, §9 :548）

§5 の定数表は3つの値を並べているが、**互いの順序関係を書いていない。**

```
γ_base_min  要測定（暫定 0.40）  ← 実測した発振閾値 + マージン
γ_base_max  暫定 0.60           ← 「第1レジスタを維持できる上限。跳躍閾値未満」
γ_ceiling   暫定 0.95           ← 「跳躍閾値より上」
```

一方 §9 テスト6 は**発振閾値が `0.2 < γ < 0.6` のどこかにある**としか主張していない。

→ 測定した発振閾値が 0.55 なら `γ_base_min ≈ 0.60`（+マージン）となり
`γ_base_max = 0.60` と**一致してベロシティのダイナミックレンジが消える**。
閾値が 0.6 に近ければ `γ_base_min > γ_base_max` で**範囲が反転**し、
`γ_base = γ_base_min + velocity01·(γ_base_max − γ_base_min)` の傾きが負になる
（＝強く弾くほど弱くなる）。設計書にはこの状態を検出する記述が無い。

実際には5つの量に順序制約がある。**どこにも書かれていない:**

```
γ_th_osc  <  γ_base_min  <  γ_base_max  <  γ_th_jump  <  γ_ceiling  ≤  0.95
（発振閾値）              （実測）      （跳躍閾値）
```

`γ_th_osc` と `γ_th_jump` はどちらも §10 手順6 で実測する量。
**測定結果がこの不変条件を満たす保証は無い。** 特に `γ_th_jump − γ_th_osc` が狭ければ
`γ_base_max < γ_th_jump` と `γ_base_min > γ_th_osc` が両立しない。

**要対応**:

1. 上の不変条件を §5 に1行で明記する
2. 手順6 で測った値がこれを満たすかを**実行時 assert またはテスト**にする
3. 満たさない場合の縮退方針を決める（例: `γ_base_max = γ_th_jump − マージン` を優先し、
   ベロシティレンジが狭ければそれを受け入れる／`γ_ceiling` を 0.95 未満に下げる）

### R49. 発振閾値は4つのユーザーパラメータで動くのに `γ_base_min` は単一定数（§5 :376, §6 :402）

`γ_base_min` は「実測した発振閾値 + マージン」と定義された（R24 の修正）。
だが**発振閾値は既定パラメータ限定の量**で、次のスライダーすべてで動く:

| パラメータ | 範囲 | 閾値への効き |
|---|---|---|
| `zeta` | 0.05 – 0.8 | 小さいほど結合が弱く閾値が上がる。**0.05 では全 γ で発振しない可能性** |
| `bellCutoff` | 200 – 5000 Hz | 低いほど損失増 → 閾値が上がる |
| `wallLoss` | 0.90 – 1.0 | 0.90 は1往復 10 % 損失 → 閾値が大きく上がる |
| `reedFreq` | 300 – 5000 Hz | リードのリアクタンスで閾値が動く |

→ 既定値から離れたスライダー位置では `γ_base` が閾値を下回り、
**弱打鍵どころか全打鍵が無音**になりうる。R24 で潰した失敗モードが、
パラメータを動かした瞬間に戻ってくる。

**要決定**: どちらか。

- (a) **受容して明記する** — 「損失を上げる／アンブシュアを締めると鳴らなくなるのは
  実物と同じ挙動」として §5 に書き、手動受け入れ基準に
  「`wallLoss` を下限にすると発音しなくなること」を積極的に載せる。
  実装は変わらない。おそらくこれが正しい
- (b) `γ_base_min` を現在のパラメータから安価に推定して追従させる（複雑さに見合わない）

(a) を選ぶ場合でも、**「γ_base_min は既定パラメータでのみ校正されている」と
書いていない現状は不備**。R24 の修正が「どの設定でも鳴る」と読めてしまう。

### R50. DC ブロッカが `tanh` の**前**にあり、記述された根拠と矛盾する（§4.4 :259, §4.5 :306）

```
§4.4 手順9  out[0] ← (1+R)·p⁺_bell → DC ブロッカ → tanh リミッタ → 非有限を 0 に
§4.5 :306   out[0] は (1+R) 透過音 → DC ブロッカ（tanh 後の偶数次対策の保険）→ tanh リミッタ
```

括弧書きは「**tanh 後**の偶数次対策」と言っているのに、ブロッカは **tanh の前**にある。
tanh が作る成分を、tanh より前のブロッカは除去できない。

`tanh` は奇関数だが、**入力が平均 0 でも非対称なら出力に DC が出る**。
クラリネットのビーティング波形はデューティ比が 50 % でない非対称波。

数値例（+0.9 が 25 %、−0.3 が 75 %、平均 0）:

```
tanh(0.9) = 0.7163,  tanh(−0.3) = −0.2913
出力平均 = 0.25·0.7163 + 0.75·(−0.2913) = −0.0394
出力 RMS = 0.438      →  |平均|/RMS = 9.0 %
```

§9 テスト19 は「`out[0]` の平均が振幅 RMS の **1 % 未満**」を要求し、
**チェーンの最後**（＝ tanh の後）を測る。tanh が深く効く領域ではテスト19 が落ちる。

**要決定**: DC ブロッカを `tanh` の**後**に移す（または前後に1つずつ置く）。
そのうえで §4.5 の括弧書きの根拠と位置を一致させる。

### R51. `read-before-write` 規約が §4.4 の手順順序と字面上矛盾する（§4.5 :272, §4.4 :255-257）

§4.5 の規約: 「各線は同一サンプル内で**読んでから書く**（read-before-write）」

§4.4 の手順: リード→ベル線を**手順6 で書き、手順8 で読む**（write-before-read）。

§0.2 で追跡したとおり**結果としての総遅延は 2D で正しい**（`D ≥ 1` なら
読み書きの文の順序は総遅延に影響しない。効くのはインデックスの差だけ）。
だが規約が文の順序として書かれているため、

- §4.4 を読んだ実装者が「規約に反している」と判断して手順6 と 8 を入れ替える
- あるいは `tick()` 型の遅延線クラスを使い、内部でポインタを進めて `D+1` になる

のどちらかが起きうる。**R28 で潰したはずの off-by-one が戻る経路。**

**修正案**: 規約を文の順序ではなく**インデックス関係**として書く。

```
各遅延線は長さ D_eff の循環バッファ。書き込み位置 w に対し
    読み出し位置 = w − D_eff        （小数部は線形補間）
読み書きの記述順序は総遅延に影響しない（D_eff ≥ 1 のため）。
ポインタを進めてから読む実装（tick 型）にすると D_eff + 1 になるので使わない。
```

テスト9 がこれを検証するので、規約の文言だけの問題ではあるが、
テスト9 が落ちたときに何を直すべきかが規約から読み取れる必要がある。

### R52. oversample 切替時に `D_eff`（グライド状態）を再導出するか未定義（§4.6 :323-325）

「係数と `D` を再計算し、遅延線の中身を新レートへ線形リサンプル、`out[0]` を 5 ms フェード」。

`D_eff` は §4.5 で**1極グライドの内部状態**（τ_D = 15 ms）になった。
`D`（目標値）を再計算しても、`D_eff` が旧レートの値のままなら
グライドが新目標 `2·D` へ 15 ms かけて向かう → **1オクターブ下から上がってくるピッチグライド**。

フェードは 5 ms、グライドは 15 ms（静定 45 ms）なので**フェード明けに聞こえる**。

**要対応**: 切替時に `D_eff ← D_eff × (fsInternal_new / fsInternal_old)` と即座に再導出する
（グライドさせない）。§4.6 に1行。

### R53. パネル3 で `p⁻` の空間軸を反転しないと定在波が誤って描かれる（§7 :463）

`p⁺` はリード→ベル線、`p⁻` はベル→リード線。**2本のバッファはインデックスの向きが逆**。

- `p⁺` はバッファ先頭がリード端寄り
- `p⁻` はバッファ先頭がベル端寄り（波が逆向きに走るため）

同じ管軸 `z` 上に並べるには**片方を反転**する必要がある。反転せずに
`p⁺[i] + p⁻[i]` を「和」として描くと、**定在波の節・腹の位置が物理と一致しない**。

中心要件3（導波路内の共鳴状態が見えること）と、要件1 の検証手段
（「節・腹の数が 1→3 に変わる瞬間が見える」）が静かに壊れる。
§9 :651 が認めるとおりパネルの描画は目視のみなので、**気付きにくい**。

**要対応**: §7 に「`pMinus` は反転して同じ `z` 軸へ写す」と明記。
`z=0` をリード端、`z=nTube` をベル端に固定する。

補足: これを検証可能にするなら、`pPlus + reverse(pMinus)` の和が
既知の f0 に対して `nTube` 区間に節を「(2k+1)/4 波長」の位置に持つ、
というテストが書ける（→ T12 と同系統）。

### R54. `out[1]` に非有限ガードが掛からない（§4.4 :258-259, §8 :514-516）

§8 が新設したサンプル毎の非有限ガードは **§4.4 手順9 の `out[0]` 側にだけ**書かれている。
`out[1] ← p̃` は素通し。

発散時、ブロック末のリセットまで最大 128 サンプルの `NaN` が `out[1]` → `AnalyserNode` へ入る。
`getFloatTimeDomainData` が `NaN` を返す → **自己相関が `NaN` を返し、裏返りインジケータが壊れる**。
`fftSize = 2048`（42.7 ms）の窓なので、1回の発散で **43 ms 分の表示が汚染**される。

`out[1]` は `destination` に繋がないのでスピーカーの危険は無いが、
UI の復帰が `diverged` 通知だけに依存する。

**要対応**: 同じサンプル毎ガードを `out[1]` にも掛ける。1サンプル1比較。

### R55. テスト17 の期待値が「期待どおりに分岐」で実装できない（§9 :585-587）

「同じ γ 軌跡を (a) 長さ `blockLen` の配列、(b) 長さ 1 の配列（k-rate 相当、値一定）で与え、
**期待どおりに分岐すること**」

「期待どおり」が何かが書かれていないので、テストとして起こせない。

**修正案**: 具体的な不変条件にする。

```
定数 v に対し:
  process(blockLen, { gamma: new Float32Array([v]) })
    ≡ process(blockLen, { gamma: Float32Array.from({length: blockLen}, () => v) })
  出力がビット一致すること
```

これで「長さ1配列を配列の先頭要素としてしか読まない」「毎サンプル
`arr[i]` を読んで範囲外アクセスする」の両方を捕まえられる。
T9 の意図はこの assert だった。

### T10. `gate × gamma` の積の経路にテストが無い ★

R25 の修正で `gamma` と `gate` を2本の a-rate `AudioParam` に分け、
**worklet 内で積を取る**構造になった（§5 :339, §6 :419）。
この積が正しく取られているかを見るテストが無い。

**案**: `(gate, gamma) = (1.0, 0.5)` と `(0.5, 1.0)` と `(0.7071, 0.7071)` で
出力が一致すること（積 = 0.5 が同じなので）。
併せて `gate = 0` で常に無音（`γ = 0` → テスト5 と同じ結論）になること。
分離のミス（片方だけ読む、加算になっている）を捕まえる。

### T11. `D_eff` グライドの `|dD/dt| < 1` 制約にテストが無い ★

§4.5 :300-302 が**新しく制約として明文化**した
「`τ_D` を 3 ms 未満にしてはならない」。制約を書いただけで検証していない。

**案**: `τ_D` をコンストラクタ引数にし、
`τ_D = 15 ms` で最大跳躍 `ΔD = 147` を与えたとき
`|D_eff[n] − D_eff[n−1]| < 1` が全サンプルで成立すること。
併せて `τ_D = 2 ms` では成立しない（＝制約が実在する）ことも確認しておくと、
定数を後から縮めたときに気付ける。

### T12. 2× 切替後のループ遅延にテストが無い ★（R52）

テスト9（ループ全遅延 = `2·D_eff`）は 1× を想定している。
2× 切替では `D` が倍になり遅延線がリサンプルされるので、
**切替後に総遅延が `2·D_eff(new)` に戻っているか**が別の検証対象。
R52（`D_eff` の再導出）のバグはここでしか捕まらない。

**案**: 1× で定常発振させ、`setOversample(2)` 相当を呼び、
フェード明け（5 ms 後）+ グライド静定後の f0 が切替前と ±1 % 以内。
`D_eff` をグライドさせてしまう実装なら、切替直後の f0 が 1 オクターブずれて落ちる。

### T13. 出力段の非有限ガードが「同じブロック内」で効くことを検証していない

テスト20 は内部状態に `Infinity` を注入し「**以降の**出力が有限」を見る。
だが §8 :514-516 が新設した**サンプル毎ガード**の役割は
「ブロック末のリセットが走る**前の最大 128 サンプル**」を守ることなので、
「以降」しか見ないテスト20 では**この機構を外しても通る**。

**案**: 注入した**そのブロック**の 128 サンプル全部が有限であることを assert。
R54 を採るなら `out[1]` についても同じ assert。

### 分類について

§9 の「検出できない不具合」節は改訂2 で妥当になっている。
`performance.now()` の可用性（:631）を「ブラウザ経路」に入れたのは正しい。
パネルの描画を目視のみとしたのも妥当だが、**R53（`p⁻` の反転）だけは
数値テストで捕まえられる**ので、上の T12 と同系統でテスト化する余地がある。
