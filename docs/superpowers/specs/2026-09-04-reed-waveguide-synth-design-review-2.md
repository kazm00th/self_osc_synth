## 重 — 実装前に決めないと後戻り

### R24. `γ_base` の下限 0.30 が発振閾値を下回る（§6 :310, §9 :414-415）

```
γ_base = 0.30 + velocity01 · 0.25   → [0.30, 0.55]
```

一方 §9 テスト5 は「準静的理論値は 1/3」と書いている。**1/3 = 0.3333 > 0.30**。
さらに損失があると実閾値は 1/3 より**上**へずれる（設計書自身が §9 :415 で認めている方向）。

→ `velocity01` が小さい打鍵は **γ_target < 閾値 で確実に無音**になる。
`expressionSource = なし` を選ぶと `expr01 = 0` なので `γ_target = γ_base` そのもの。
弱打鍵が鳴らない楽器になる。

加えて構造上の問題: 閾値は §10 手順6 で実測すると決めたのに、
`γ_base` の下限・上限は実測前に固定値で書かれている。テスト5 と同じ循環。

**要決定**: `γ_base` の下限を実測閾値から導出する（例: 閾値 + マージン）か、
手順6 で確定する定数として明示的に TODO 化する。

### R25. `gateEnv × γ_target` と単一 `setTargetAtTime` が両立しない（§6 :317, :325）

設計書は2通りの記述を並べている。

```
:317  γ(t) = gateEnv(t) · γ_target                            ← 2つの包絡の積
:325  gamma.setTargetAtTime(γ_target, now, τ_short ≈ 0.02)    ← 単一の自動化
```

`gamma` は1本の `AudioParam`。2つの包絡を掛けることはできない。
main 側で積を計算して書くしかないが、そうすると**同じ `AudioParam` に対して
ゲート（τ = release）と表現（τ_short = 0.02）が異なる時定数で書き込む**ことになる。

`setTargetAtTime` は後続の呼び出しが先行のターゲットを打ち切る。
→ **ノートオフのリリース中にホイール／ブレスを動かすと、リリースが取り消されて
音が戻る**（意図しないリトリガ）。

**要決定**: どちらか。

- (a) main 側で `gateEnv × γ_target` を常時計算し、単一の時定数で `setTargetAtTime` する
- (b) `gamma`（表現ぶん）と別に `gate` パラメータを設け、worklet 内で積を取る

(b) のほうが時定数の衝突が起きない。

### R26. ブレス(CC2)がモジュレーションと同一写像に退化した（§6 :313-314, :323）

改訂後は両ソースとも `静止 0 → γ_base` の同じ写像になった（:323 で明言）。
結果、**セレクタは3択だが挙動は実質2種**（ブレス ≡ モジュレーション、なし = `expr01` を 0 固定）。

これは R6 の修正の副作用で、初版が持っていた物理的整合性を失っている:

- §1 の表は「直流エネルギー源 = 吹圧 γ」。初版 §6 は「息のエンベロープ = 吹圧そのもの、
  だから物理的に正しく、立ち上がりの過渡（チフ音）が自然に出る」と書いていた
- 改訂後は息を止めても `gateEnv` が 1 のかぎり `γ_base` で鳴り続ける。
  息では音を止められず、`γ_base` より弱くも吹けない

**修正案**: 天井打ちを起こさずにソース別写像へ戻せる。

```
ブレス(CC2)          : γ_target = expr01 · γ_ceiling                      → [0, 0.95]
                       gateEnv はノート在否のマスクのみ
モジュレーション(CC1) : γ_target = γ_base + expr01·(γ_ceiling − γ_base)   → 現行のまま
なし                 : γ_target = γ_base                                  → 現行のまま
```

どの経路も 0.95 を超えないのでクランプ不要。R6 の原因（倍率の積み上げ）は再発しない。

### R27. 2× 時に `out[1]`（p̃）のデシメーションが未定義（§4.6 :259, §3 :80）

§4.6 は「出力の間引きは 15 タップの窓関数付き sinc ハーフバンド FIR」と書くが、
**`out[0]` のことしか言っていない**。`out[1] = p̃` も `fsInternal = 96 kHz` で生成されるので、
そのまま 48 kHz の出力バッファへ書くと 1 サンプル飛ばしの単純間引き = 折り返し込み。

`out[1]` は §6 の裏返りインジケータ（自己相関）と §7 パネル4 のスペクトルの唯一の入力。
**エイリアスした p̃ で自己相関を取れば f0 推定が壊れる。**

**要決定**: `out[1]` にも同じハーフバンド FIR を通す（FIR 状態を2系統持つ）。
CPU は増えるが、インジケータの正しさが `out[1]` の帯域制限に依存している。

### R28. ループ全遅延の規約が未定義 — 短管で系統的にピッチがずれる（§4.4, §4.5）

§4.4 は「手順1で `p⁻` を読む / 手順6で `p⁺` を書く / 手順8でベル端を折り返す」と順序を決めたが、
**遅延線のインデックス規約（往復の総遅延が `2D` か `2D+1` か `2D+2` か）を決めていない。**

`f0 = fsInternal/(4·D_eff)` なので、`D_eff` が 2 サンプルずれると:

| L | D | 2サンプル誤差の影響 |
|---|---|---|
| 1.2 m | 168 | 0.30 % ≈ 0.05 半音 |
| 0.15 m | 21 | **2.4 % ≈ 0.41 半音** |

テスト6 は ±5 % 許容なので**この系統誤差を検出できない**。
テスト10 は補間器の検証であって、ループ全長の検証ではない。

**要対応**: (1) 遅延線の読み書きインデックス規約を §4.4 か §4.5 に明記する。
(2) 総ループ遅延を直接測るテストを足す（→ 後述 T2）。

## 中

### R29. snapshot の可変長配列が「一切アロケートしない」と矛盾（§3 :85, §7 :363）

§7 は `pPlus`, `pMinus` を各 `min(D, 256)` とした（R8 の修正）。
だが `D` は `tubeLength` で変わるので、長さが変わるたびに新しい `Float32Array` が要る。
§3 :85 の「**audio thread では一切アロケートしない**」に反する。

**修正案**: 固定長 256 のバッファを確保したまま、snapshot に `nTube = min(D, 256)` の
整数フィールドを1つ足し、UI 側が先頭 `nTube` 要素だけを使う。
（:365 のサイズ計算は 256 固定を前提にしているので、そちらとも整合する。）

### R30. 自己相関の前の平均除去が未記述（§6 :336）

`out[1] = p̃` はマウスピース内圧。発音中の平均値は 0 ではない（γ に依存した正のオフセットを持つ）。
DC 成分が乗ったまま自己相関を取ると、相関関数が DC 項に支配されて
ラグに対してほぼ平坦になり、ピーク検出が不安定になる。

**要対応**: 自己相関の前に窓内平均を引く（または1次ハイパスを掛ける）ことを明記。
倍音列マッチングを使う場合も 0 Hz bin を除外する。

なお `out[0]` は `(1+R)` と DC ブロッカで DC が除かれているが、
インジケータの入力は `out[1]` なので恩恵を受けない。

### R31. §7 パネル1 の「閉鎖中の平坦部」は現行モデルでは出ない（§4.1, §4.2, §7 :351）

§4.1/§4.2 のモデルは `x` を 0 でクランプせず、**`x < 0` でも線形 ODE を回し続け、
流量だけを `max(x,0)` で 0 にする**（減衰は `contactQ` 倍）。
つまり閉鎖中も `x` は 0 以下へ動き続ける。相図に**平坦部は現れない**。

平坦部が見えるのは `x = max(x, 0)` のハード・クランプか接触剛性を入れたモデル。

**要決定**: (a) §7 の記述を実態に合わせる（「x<0 側へ減衰しながら潜る区間」）か、
(b) 接触剛性/クランプを §4.1 に足す。
(b) を選ぶ場合は「係数2組の切替」では足りず、モデルが変わる。

補足: 減衰だけを増やす接触モデルは、実物のリードがレイに巻き付くときの
**剛性**増加を表していない。簡略化として妥当だが、非目標に書かれていない。

### R32. `performance.now()` の AudioWorkletGlobalScope 可用性が未確認（§7 :376）

`AudioWorkletGlobalScope` に露出しているのは `currentTime` / `currentFrame` / `sampleRate` が中心で、
`performance` は仕様上 `Window` と `Worker` に露出するもの。Worklet での可用性はブラウザ依存。

**要対応**: 実装前に1行で可用性を確認する。使えない場合の代替:

- `AudioContext.renderCapacity`（Chrome 112+）— まさにこの用途の API。main 側から取れる
- main 側で `AudioContext.currentTime` の進みと `performance.now()` の比から推定

### R33. 透過 `(1+R)` に `wallLoss` が入らず反射 `wallLoss·R` と非整合（§4.5 :241, :248）

反射は `wallLoss·R(z)`、透過は `(1+R)` と書かれている。
`R` と `1+R` の相補関係が `wallLoss` の分だけ崩れる。

`wallLoss` は本来は管全体に分布する損失をベルに集約した近似なので、
透過側に入れない選択自体は妥当。ただし**意図的であることを明記しないと、
後から「バグでは」と読まれる**。テスト14（受動性）の解釈にも効く。

### R34. `γ_ceiling = 0.95` の「跳躍閾値より上」は未測定の仮定（§6 :311）

R24 と同根。跳躍が起きる γ は §10 手順6 で実測すると決めている。
0.95 で跳躍領域に届くかは未確認。届かなければ「意図的に12度へ追い込む」が実現しない。

**要対応**: 手順6 で確定する定数として TODO 化する（R24 とまとめて1箇所に）。

### R35. テスト15（1× vs 2× の一致）は前提が自己矛盾（§9 :438-439）

「1× と 2× で第1–5倍音の相対レベルが ±3 dB 以内」。
だが**オーバーサンプリングを入れる理由は 1× と 2× でスペクトルが違うから**（§4.6 :255）。

- 一致するなら 2× は不要
- 不一致なら正しい実装でもテストが落ちる

低次倍音（1–5）はエイリアスの影響が小さいので通る可能性はあるが、閾値の根拠がない。

**修正案**: 「2× の実装ミス検出」が目的なら、**2× と 4×（テスト専用の参照レート）を比較**する。
1× vs 2× は f0 と総 RMS だけに絞る。

### R36. テスト16 の基準「静定時の最大値」の測定条件が未定義（§9 :440-441）

「`tubeLength` を 50 ms かけて端から端へ動かし、隣接サンプル差が**静定時の最大値**の 3 倍を超えない」。

隣接サンプル差は f0 に比例して大きくなる（同じ振幅でも短管ほど大きい）。
基準を掃引開始側（L=1.2 m, 71 Hz）で取ると、終端（L=0.15 m, 572 Hz）では
**8倍の周波数比だけで 3 倍の閾値を超える**。正しい実装でも落ちる。

**修正案**: 終端 L で測った静定値を基準にする、または
「局所的な線形予測からの跳び」を見るクリック検出器に変える。

### R37. テスト14「共鳴器単体の受動性」が名前どおりでない（§9 :436-437）

「`γ = 0` でリード端にインパルスを入れ、遅延線のエネルギーが単調減少」。

- `γ = 0` でもリードは開いている（`x → 1`）ので `ζ·X ≠ 0`。
  リード端は**非線形抵抗性終端**であって、無反射でも完全反射でもない。「共鳴器単体」ではない
- 進行波エネルギー `Σ(p⁺² + p⁻²)` は波が管内を移動するだけでサンプル毎には揺れる。
  **サンプル毎の単調減少は成立しない**

**修正案**: `X = 0` を強制（リードを閉じたまま）して完全反射終端にし、
エネルギーは**1往復 `2D` サンプルごと**に評価する。それなら
「1往復あたりゲイン ≤ wallLoss」という明確な主張が検証できる。

## テストの漏れ

§9 の 16 本は前回より大きく改善している（11 ブロック境界不変性、12 決定性、13 長時間安定性、
16 ランプ滑らかさは特に有効）。以下は残った穴。

### T1. 係数切替（開放↔接触）の連続性テストが無い ★

§4.1 が直接形 IIR を捨てて TPT 状態空間を採用した**唯一の根拠**が「係数切替が連続」。
その根拠自体を検証するテストが無い。

**案**: `x` が 0 を跨ぐ区間で、切替の前後 1 サンプルの `(x, x')` の差が
連続 ODE から予測される変化量の許容倍率内であること。
あるいは、同一サンプルで `k` を切り替えても `(s1, s2)` が変化しない（構造上の不変量）ことを直接 assert。

### T2. ループ全遅延 = 2D の直接検証が無い ★（R28）

**案**: `X = 0` を強制して完全反射にし、リード端にインパルスを入れて
戻ってくるまでのサンプル数が厳密に `2D` であることを確認（`delaySamples` 直接指定、整数 `D`）。
テスト6 の ±5 % では隠れる off-by-one を確実に捕まえる。

### T3. `src/midi.js` の純関数が一切テストされていない ★

§9 の対象は `worklet/reed-tube-processor.js` のみ。だが

- γ 写像（§6 :309-319）— **R6 のバグが起きた場所**
- ノート → `L` 変換とクランプ（§6 :296-298）— **R10 の誤りが起きた場所**

はどちらもブラウザ非依存の純関数。両方とも過去に実際に誤っている。

**案**: `src/midi.js` から `noteToLength(note)` と `computeGammaTarget(velocity01, expr01, source)`
を副作用なしで export し、`tests/midi.test.js` で検証。
`γ_target ≤ 1.0` の不変条件、`expr01 = 0 → γ_base`、単調性、クランプ境界（MIDI 37/38, 74/75）。

### T4. f0 推定器のテストが無い ★

§9 :471 は「裏返りインジケータの f0 推定の精度」を「**自動テストで検出できない**」側に分類しているが、
自己相関も倍音列マッチングも `Float32Array` を受けて数値を返す純関数で、ブラウザは要らない。**分類が誤っている。**

**案**: 合成波形で検証する。

- `f + 3f + 5f`（**3f を基音より 6 dB 大きく**）+ DC オフセット → `f` を返すこと（R2 の失敗モードそのもの）
- f = 71 Hz（最長管）と 572 Hz（最短管）の両端
- 第2レジスタ相当（`3f` 主体）で `3f` を返すこと
- 比の判定が 1 近傍 / 3 近傍で正しく分かれること

インジケータが系統的に誤ったまま全テストが通る、という §9 自身が挙げた懸念が、これで消える。

### T5. ハーフバンド FIR 係数のテストが無い

15 タップの係数配列は定数。**案**: 係数の対称性、DC 利得 = 1、
`fsInternal/4` で −6 dB、阻止域減衰が目標値以上。純関数。

### T6. `b = 0` 近傍の分岐連続性テストが無い

テスト1–3 は残差・符号・`X=0` を見るが、**2分岐の継ぎ目**を見ていない。
**案**: `b` を `−ε … +ε` で掃引し `ũ(b)` が連続かつ単調。分岐の実装ミス（不等号の向き、片側の符号）を捕まえる。

### T7. 出力 DC の絶対量テストが無い

§9 :477 が「DC ドリフトの絶対量は未評価」と認めている。
**案**: 既定パラメータで定常後 5 秒の `out[0]` の平均が振幅 RMS の 1 % 未満。
`(1+R)` と DC ブロッカが効いているかの直接確認。安い。

### T8. 発散ガード自体のテストが無い

§8 の復帰経路は一度も実行されないまま出荷されうる。
**案**: モデルの内部状態に人為的に `Infinity` を注入し、次の `process()` でリセットが働き、
以降の出力が有限かつ 5 ms でフェードインすることを確認。

### T9. a-rate パラメータ配列の扱いのテストが無い

§9 :448 は「a-rate パラメータ配列の読み違い（テストはオフラインでスカラー入力しがち）」を
「検出できない」側に置いている。だが `ReedTubeModel` が**長さ 128 の配列と長さ 1 の配列の両方**を
受け付ける設計なら、ヘッドレスで検証できる。§3 :126-129 のテスト可能性要件に1行足すだけ。

**案**: 同じ γ 軌跡を (a) 長さ 128 の配列、(b) 128 回のスカラー呼び出し で与えて出力一致。
AudioWorklet が k-rate 時に長さ 1 の配列を渡す仕様（値一定）の分岐も同時に検証。

### 分類の訂正（§9「検出できない不具合」）

現行の分類のうち、次の2つは**実際には自動テストできる**ので移すべき:

- 「裏返りインジケータの f0 推定の精度」（:471）→ T4
- 「a-rate パラメータ配列の読み違い」（:448）→ T9

残り（配線・レイテンシ・音色・ヒステリシス・CPU・参照比較の不在）の分類は妥当。
